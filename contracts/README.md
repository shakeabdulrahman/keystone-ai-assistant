# Contracts

The agreement between the AI gateway (`backend/`) and the apps (`mobile/`). Both test suites load the files in `fixtures/`, so a change on one side that breaks the other fails CI. The full, generated OpenAPI spec is served at `/openapi.json` (and `/docs`) when the backend runs locally.

## Authentication

Every `/v1` endpoint except `/v1/meta` requires `Authorization: Bearer <Firebase ID token>`. The backend verifies the token's signature, audience (project ID), issuer and expiry. A missing or invalid token returns `401` with `WWW-Authenticate: Bearer` and code `unauthorized`; the app should refresh the token once and retry, then send the user to sign-in.

Local development (`AUTH_MODE=dev`, refused in production): tokens look like `dev:<user>` or `dev:<user>:<email>`, and requests with no token act as `dev-user`.

## Endpoints

| Method | Path | Notes |
| --- | --- | --- |
| POST | `/v1/auth/session` | Call after sign-in. Creates the user on first visit; returns the profile |
| GET | `/v1/me` | Profile: `id`, `email`, `display_name`, `role`, `created_at` |
| DELETE | `/v1/me` | Permanently deletes the user and all their conversations (`204`) |
| POST | `/v1/chat` | Send a message; streams the reply (below) |
| GET | `/v1/conversations?limit=20&cursor=` | Newest first. `{items: [{id, title, created_at, updated_at, last_message_at}], next_cursor}` |
| GET | `/v1/conversations/{id}` | One conversation (`404` if missing or not yours) |
| GET | `/v1/conversations/{id}/messages?limit=50&cursor=` | `{items: [{id, role, content, status, created_at, parts}], next_cursor}`. Items are oldest first; `next_cursor` loads **older** messages. `parts` lists the answer's tool results (`type: "tool_result"`, `call_id`, `tool`, `status`, `ui`, `data`) and its sources (`type: "citations"`, `items` as in the `citations` event), so history shows the same cards and sources. Clients skip part types they don't know |
| GET | `/v1/home` | The dashboard (shape below) |
| POST | `/v1/devices` | `{token, platform: "android"/"ios"}` registers this phone for push (`204`, idempotent). A token moves to whichever account registers it last |
| POST | `/v1/devices/unregister` | `{token}`, on sign-out (`204`) |
| GET | `/v1/actions/{id}` | An action the assistant proposed (shape below). `404` if missing or not yours |
| POST | `/v1/actions/{id}/confirm` | Runs it. **Idempotent**: confirming an executed action returns the same result. `200` with `status: executed` (and `result`) or `status: failed` (and a user-facing `error.message`; nothing changed). `409` with `code` `action_expired`, `action_cancelled`, `action_in_progress`, `action_done` or `action_failed` when it can't run |
| POST | `/v1/actions/{id}/cancel` | `200` with `status: cancelled` (repeatable). `409` if already executed |
| GET | `/v1/documents` | Policy documents: `{items: [{id, title, version, effective, owner, updated_at}]}` |
| GET | `/v1/documents/{id}` | One document with `sections: [{index, heading, body}]` (`body` is Markdown). A citation's `section_index` is an index into `sections`. `404` if unknown |
| PATCH | `/v1/conversations/{id}` | `{title}` (1–120 chars) |
| DELETE | `/v1/conversations/{id}` | Removes it from the user's list (`204`) |

Pagination is keyset-based: pass `next_cursor` back as `cursor` until it is `null`. Cursors are opaque strings. Message `status` is `complete`, `interrupted` (user stopped or disconnected) or `failed`.

A new conversation's title starts as the first question (shortened) and is replaced by a short AI-generated title after the first answer, unless the user renames it.

## Chat stream (`POST /v1/chat`)

Request (JSON):

| Field | Type | Notes |
| --- | --- | --- |
| `conversation_id` | UUID, optional | Omit to start a new conversation; must belong to the caller |
| `client_message_id` | UUID | Generated by the app per message; a duplicate returns `409` |
| `content` | string, 1–4000 chars | Trimmed; blank is rejected with `422` |
| `input_mode` | `"text"` (default) or `"voice"` | `voice`: the question was spoken and the answer will be read aloud, so it comes back as short spoken sentences without lists or markdown |

Response: `text/event-stream`. Errors **before** the stream starts are normal HTTP problem+json responses (`404` unknown conversation, `409` duplicate, `422` validation). Errors **during** the stream arrive as an `error` event.

Each event is an SSE frame:

```
event: <type>
data: {"seq": <n>, ...payload}

```

Lines starting with `:` are keep-alive comments and carry no data.

| Event | Payload | Client should |
| --- | --- | --- |
| `message.started` | `conversation_id`, `message_id`, `user_message_id` | Remember the conversation ID; show an empty streaming bubble. `message_id` is the ID the answer is stored under |
| `text.delta` | `text` | Append text to the bubble |
| `message.completed` | `message_id`, `finish_reason` (`stop`/`length`), `usage` {`input_tokens`, `output_tokens`} | Mark the message complete |
| `tool.started` | `call_id`, `tool`, `label` (e.g. "Checking your leave balance") | Show a progress row with the label |
| `tool.result` | `call_id`, `tool`, `status` (`ok`/`error`), `ui` (card type or null), `data` (object) | Replace the progress row with the card for `ui`; on error, a short "couldn't load" note |
| `confirmation.required` | `action_id`, `tool`, `title`, `fields[]` {`label`, `value`}, `notes[]`, `confirm_label`, `expires_at` | Show a confirmation card with exactly these fields and two buttons: `confirm_label` (→ `POST /v1/actions/{action_id}/confirm`) and Cancel (→ `/cancel`). Nothing has changed yet |
| `citations` | `items[]`: `ref` (the number in the text, `[1]`), `document_id`, `title`, `section_index`, `heading`, `snippet` (plain text) | Show source chips under the answer; open `GET /v1/documents/{document_id}` at `section_index` when tapped |
| `error` | `code`, `message` (safe to show), `retryable` | Show the message; offer Retry if `retryable` |

Order: `message.started`, then any mix of `text.delta` and `tool.started`/`tool.result` pairs (same `call_id`; a write tool's `tool.result` is followed by at most one `confirmation.required` per answer), then at most one `citations` (only sources the answer cited), then exactly one of `message.completed` or `error`. A model may call several tools, over several steps, before or between text.

**Forward compatibility:** clients must ignore event types, fields and `ui` card types they don't recognise.

### Tool cards (`ui` → `data`)

All dates are ISO 8601 (`2026-10-15`, or full timestamps for meetings and notifications).

| `ui` | `data` |
| --- | --- |
| `profile` | `name`, `email`, `job_title`, `department`, `manager`, `location`, `start_date` |
| `leave_balance` | `year`, `unit`, `items[]`: `type`, `entitled`, `used`, `remaining` |
| `leave_requests` | `filter`, `items[]`: `id`, `type`, `start`, `end`, `days`, `status` (`pending`/`approved`/`rejected`), `submitted_on` |
| `hr_requests` | `filter`, `items[]`: `id`, `category`, `title`, `status` (`submitted`/`in_progress`/`resolved`), `updated_on` |
| `tasks` | `filter`, `items[]`: `id`, `title`, `category`, `due`, `status` (`pending`/`done`), `overdue` |
| `appointments` | `filter`, `items[]`: `id`, `title`, `with`, `start`, `end`, `location` |
| `notifications` | `items[]`: `id`, `title`, `body`, `created_at`, `read` |
| `null` for write tools | `action_id`, `status: "awaiting_confirmation"`, `summary`. The card comes in `confirmation.required` |
| `policy_search` | `query`, `results[]`: `ref`, `document`, `section`, `text`; `note` when nothing matched. Meant for the model; apps may show nothing and rely on `citations` |

Results larger than the size limit carry `"truncated": true`.

Error codes: `ai_unavailable`, `ai_timeout`, `ai_rate_limited` (retryable), `ai_misconfigured` (not retryable), `internal_error` (retryable).

## Actions (Phase 5)

Write tools (`submitLeaveRequest`, `cancelLeaveRequest`, `createHrRequest`, `completeTask`) never change anything when the model calls them. They store a proposal and stream `confirmation.required`. The change runs only on `POST /v1/actions/{id}/confirm`, with the arguments frozen at proposal time.

Action shape (`GET`, `confirm`, `cancel`):

```json
{"id": "…", "tool": "submitLeaveRequest", "status": "executed",
 "title": "Request annual leave", "fields": [{"label": "Dates", "value": "…"}], "notes": [],
 "confirm_label": "Submit request", "expires_at": "2026-10-15T09:15:00Z",
 "result": {"reference": "LR-1050", "message": "Leave request LR-1050 submitted. …"},
 "error": null}
```

`status`: `pending` → `executing` → `executed` | `failed`; or `cancelled`; or `expired` (15 minutes after the proposal). In `GET /messages`, a stored answer's `parts` contain `{"type": "confirmation", …the event fields…, "status", "result", "error"}`, which reflect the **current** state.

## Home (Phase 7)

```json
{"generated_at": "2026-10-15T09:00:00+00:00", "first_name": "Aisha",
 "leave": [{"type": "Annual", "remaining": 14, "entitled": 20}],
 "attention": [{"id": "task-T-301", "kind": "overdue_task", "severity": "high",
                "title": "Upload ID proof", "detail": "Overdue by 2 days",
                "action": {"type": "ask", "prompt": "Help me with my task T-301: Upload ID proof"}}],
 "upcoming": [{"id": "A-50", "title": "1:1 with your manager", "with": "Your manager",
               "start": "2026-10-22T11:00:00+00:00", "location": "Teams"}],
 "counts": {"open_hr_requests": 2, "pending_leave_requests": 1, "unread_notifications": 3},
 "suggestions": ["Which of my tasks are overdue?"]}
```

`attention` is ordered most urgent first. `kind`: `pending_action`, `overdue_task`, `task_due_soon`, `leave_pending` or `unread_notifications` (ignore unknown kinds). `action.type`:
- `ask`: open a new chat and send `prompt`.
- `open_conversation`: open `conversation_id`, where the confirmation card `action_id` is waiting.

## Push notifications (Phase 7)

FCM messages carry a generic `notification` (title "Keystone", e.g. "Your leave request has an update.") and `data` `{kind: "leave" | "hr_request", ref}`. **No HR details are ever sent in a push**: they pass through Google's servers and show on the lock screen. Opening the app shows the details (home and in-app notifications). Android channel: `hr_updates`.

## Protection (Phase 8)

Every request may carry `X-Firebase-AppCheck: <token>` (Firebase App Check). Problem codes the apps must explain:

| Status | `code` | Meaning | App behaviour |
| --- | --- | --- | --- |
| `429` | `rate_limited` | Too many requests (per IP, per user, chat, actions). `Retry-After` header and `retry_after_s` give the wait | "Try again in N seconds"; retryable |
| `403` | `app_check_failed` | `APP_CHECK_MODE=enforce` and the app couldn't prove it's genuine | Explain; not retryable |
| `503` | `auth_unavailable` | The server couldn't fetch Google's signing keys | Retry soon; **don't** sign the user out |
| `413` | `payload_too_large` | Body over 64 KB | Not retryable |

All API responses carry `Cache-Control: no-store` and standard security headers.
